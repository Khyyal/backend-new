# Keeping these docs current

These guides live in `docs-site/` and are built with [VitePress](https://vitepress.dev). They describe how the platform **behaves today**. Do not document planned features.

## The rule

A change to business behaviour is not done until the docs match. In the same change:

1. Update the matching **developer page** in `docs-site/dev/domain/<module>.md`.
2. If admins, center users or clients can see the change, update the matching **user page** in `docs-site/user/**`.
3. Look for **stale** statements, not only missing ones. Search the docs for the old behaviour.
4. Rebuild and commit the output: `npm run docs:build` (writes `storage/app/docs`).

What counts as business behaviour: status rules, pricing and fees, permissions, validation and limits, new or changed endpoints and response fields, scheduled commands, and settings.

## Adding a page

1. Create the Markdown file under `docs-site/dev/...` or `docs-site/user/...`.
2. Register it in `docs-site/.vitepress/config.mts` (`devGroups` or `userGroups`), otherwise it has no sidebar entry.
3. Link to it from related pages.

## Writing style

- Plain English, short sentences, tables for field lists and states.
- Developer pages explain rules and name the classes involved. User pages describe what a person sees and does, without class names.
- Amounts in halalas for developers; SAR for users.

## Where things are served

| Path | Content |
|---|---|
| `/guide` | These guides (built output in `storage/app/docs`) |
| `/docs` | Endpoint reference generated by Scribe |

Both need a system user with `api_docs.view`.

## Adding a language

The site is English only. To add Arabic, mirror the tree under `docs-site/ar/`, add a `locales` block to `config.mts` with `dir: 'rtl'`, and extend this rule to require both languages.
