# Recreational Riding Create/Update Service - Product Requirements Document

## Overview
- **Summary**: Implement `create()` and `update()` methods on `RecreationRidingService` that persist a Recreational Riding service through the full object graph: `Service` → `RecreationalRiding` → `PriceOption` + `Schedule`.
- **Purpose**: Provide a single entry point for creating and updating Recreational Riding services with atomic transactional integrity across all four related entities.
- **Target Users**: Callers within the Services module (future controllers, CLI commands, tests).

## Goals
- Create a Recreational Riding service with all related entities (Service record, RecreationalRiding pivot, PriceOption rows, Schedule rows) in one atomic call.
- Update an existing Recreational Riding service, including full sync of PriceOptions and Schedules (delete orphaned, create new) without requiring existing IDs.
- Wrap all persistence operations in a DB transaction to ensure rollback on any failure.

## Non-Goals
- Do NOT create FormRequest classes, controllers, routes, or API endpoints.
- Do NOT implement validation logic (to be handled upstream by FormRequests).
- Do NOT create Resource classes or modify existing models.
- Do NOT implement list/show/delete operations.
- Do NOT dispatch domain events (no event infrastructure defined for this module yet).

## Background & Context
The Services module has four related entities:
- `Service` ([Service.php](file:///Users/mac/Herd/khyyal_backend/modules/Services/src/Models/Service.php)): Base service with translatable `name`/`description` (JSON columns), `center_id`, `status`, `type` (enum `ServiceType::RecreationRiding`), auto-generated `slug` (unique per center). Has many `PriceOption`.
- `RecreationalRiding` ([RecreationalRiding.php](file:///Users/mac/Herd/khyyal_backend/modules/Services/src/Models/RecreationalRiding.php)): Pivot model with `service_id` FK. Uses `HasService` trait (provides `service()` BelongsTo + `priceOptions()` passthrough) and `HasSchedules` trait (provides `schedules()` MorphMany via polymorphic `schedulable`).
- `PriceOption` ([PriceOption.php](file:///Users/mac/Herd/khyyal_backend/modules/Services/src/Models/PriceOption.php)): Belongs to `Service`. Fields: `name` (nullable), `price` (float, nullable), `quantity` (int, nullable), `unit` (enum `PriceOptionUnit`), `service_id` FK.
- `Schedule` ([Schedule.php](file:///Users/mac/Herd/khyyal_backend/modules/Services/src/Models/Schedule.php)): Polymorphic `schedulable`. Fields: `day_of_week` (0-6), `start_time` (H:i), `end_time` (H:i).

Project constraints (from `project_memory.md`):
- Logic must reside in Service classes; controllers must remain thin.
- Use `DB::transaction` with `lockForUpdate()` for critical state transitions to avoid race conditions.
- Money values use `decimal(14,2)` — `price_options.price` is currently `float` in migration but treated as money.

## Functional Requirements
- **FR-1 (Create)**: The service SHALL expose a `create(array $data): RecreationalRiding` method that creates four entity types in order: `Service`, `RecreationalRiding`, `PriceOption[]`, `Schedule[]`.
- **FR-2 (Create — Service translatable)**: The `name` and `description` input SHALL accept an associative array with required `ar` key and optional `en` key, stored as JSON translations on the `Service` model.
- **FR-3 (Create — Service metadata)**: The created `Service` SHALL have `type = ServiceType::RecreationRiding` and `status = ActivationStatus::ACTIVE` by default. The `slug` SHALL be auto-generated by the model's `booted` hook. The `center_id` SHALL come from the input data.
- **FR-4 (Create — RecreationalRiding)**: After `Service` creation, a `RecreationalRiding` record SHALL be created referencing the new `Service` via `service_id`.
- **FR-5 (Create — PriceOptions)**: The input `price_options` array SHALL be iterated, each item containing `duration` (minutes, integer) and `price` (float). Each entry SHALL create a `PriceOption` with `quantity = duration`, `unit = PriceOptionUnit::MINUTE`, `price = price`, and `service_id` pointing to the created `Service`. The `name` field SHALL remain `null`.
- **FR-6 (Create — Schedules)**: The input SHALL accept `days` (array of integers 0-6) and `hours` (array of H:i strings with even length). For each day in `days` and each consecutive pair in `hours` (index 0&1 = slot 1, 2&3 = slot 2, ...), a `Schedule` record SHALL be created with `day_of_week = day`, `start_time = hours[2i]`, `end_time = hours[2i+1]`, and polymorphic `schedulable_type/schedulable_id` pointing to the created `RecreationalRiding`.
- **FR-7 (Update)**: The service SHALL expose an `update(RecreationalRiding $riding, array $data): RecreationalRiding` method that updates the associated `Service` (name, description) and syncs `PriceOption` + `Schedule` records without requiring their IDs.
- **FR-8 (Update — Sync PriceOptions)**: During update, all existing `PriceOption` records for the service SHALL be deleted and recreated from the input `price_options` array (full replacement sync).
- **FR-9 (Update — Sync Schedules)**: During update, all existing `Schedule` records for the `RecreationalRiding` SHALL be deleted and recreated from the input `days` + `hours` arrays (full replacement sync).
- **FR-10 (Transaction)**: All database operations within both `create()` and `update()` SHALL be wrapped in a single `DB::transaction` closure. The `Service` record SHALL be re-fetched with `lockForUpdate()` inside the transaction when performing updates that cascade to related records.

## Non-Functional Requirements
- **NFR-1 (Idiomatic Laravel)**: Code SHALL follow the conventions demonstrated in [SubscriptionLifecycleService.php](file:///Users/mac/Herd/khyyal_backend/modules/Billing/src/Services/SubscriptionLifecycleService.php): typed methods, property-promoted constructor when DI needed, `DB::transaction` closures, no raw queries.
- **NFR-2 (No inline validation)**: The Service class SHALL NOT perform validation (per project constraint: validation lives in FormRequest classes).
- **NFR-3 (Return type)**: Both public methods SHALL return the fully-loaded `RecreationalRiding` model (with `service`, `service.priceOptions`, and `schedules` eager-loaded for convenience).
- **NFR-4 (Return Fresh Instance)**: After create/update, the returned `RecreationalRiding` SHALL be a freshly-loaded instance to reflect all DB mutations.

## Constraints
- **Technical**: Must use Laravel's `DB::transaction`, Eloquent query builder `lockForUpdate()` on service row during update, project-style `PriceOptionUnit::MINUTE` enum for duration-based price options.
- **Business**: Schedules attach to the `RecreationalRiding` polymorphically (not to `Service`) per the `HasSchedules` trait placement. PriceOptions attach to `Service` directly (not to `RecreationalRiding`) per the `HasService::priceOptions()` passthrough.
- **Dependencies**: Existing modules — no new packages. Existing models unchanged.

## Assumptions
- Input data structure (as described in FRs) is validated upstream; the Service trusts array shape.
- `hours` array length is even and values are valid `H:i` strings; this precondition is enforced before the Service is called.
- `days` contains unique integers in range 0-6; precondition enforced upstream.
- `price_options` items contain non-negative `duration` and `price`; precondition enforced upstream.
- `center_id` is a valid foreign key to an existing `Center`; precondition enforced upstream via FK constraint.

## Acceptance Criteria

### AC-1: Create method persists Service with correct translations and type
- **Type**: `rule`
- **Given**: Valid input array with `center_id`, `name.ar`, `name.en?`, `description.ar`, `description.en?`, `price_options`, `days`, `hours`
- **When**: `RecreationRidingService::create($data)` is called
- **Then**: A `Service` row exists with `type = 'recreation_riding'`, `status = 'active'`, correct `center_id`, JSON `name` column containing both `ar` and `en` (en omitted if not provided), JSON `description` column containing both `ar` and `en` (en omitted if not provided)
- **Pass Condition**: Database assertion on the created Service row matches expected column values
- **Evidence**: Pest test or `DB::table('services')->where(...)` inspection after calling create

### AC-2: Create method persists RecreationalRiding referencing correct Service
- **Type**: `rule`
- **Given**: Successful call to `create()`
- **When**: Inspecting the returned `RecreationalRiding` model's `service_id`
- **Then**: It equals the ID of the newly created `Service`, and `recreational_ridings.service_id` FK constraint is satisfied
- **Pass Condition**: `$riding->service_id === Service::latest('id')->first()->id`
- **Evidence**: Eloquent relation assertion

### AC-3: Create method creates correct PriceOption records
- **Type**: `rule`
- **Given**: Input with `price_options = [['duration' => 30, 'price' => 100], ['duration' => 60, 'price' => 180]]`
- **When**: `create()` completes
- **Then**: Exactly 2 `price_options` rows exist for the new service, with `quantity = duration`, `unit = 'minute'`, `price = input price`, `name = null`
- **Pass Condition**: Row count matches, each row's columns match input mapping
- **Evidence**: `$service->priceOptions()->count()` + column-wise assertions on each row

### AC-4: Create method creates correct Schedule records (cartesian days × slot pairs)
- **Type**: `rule`
- **Given**: Input `days = [0, 2, 4]`, `hours = ["09:00", "12:00", "14:00", "17:00"]`
- **When**: `create()` completes
- **Then**: Exactly 6 `schedules` rows exist (3 days × 2 slot pairs per day), each with `schedulable_type = RecreationalRiding::class`, `schedulable_id = riding id`, correct `day_of_week` and consecutive `start_time`/`end_time`
- **Pass Condition**: Count = count(days) × (count(hours)/2), all day/slot combinations present, polymorphic FKs correct
- **Evidence**: `$riding->schedules()->count()` + iteration through all expected combinations

### AC-5: Update method updates Service translations
- **Type**: `rule`
- **Given**: Existing `RecreationalRiding` with populated Service
- **When**: `update($riding, ['name' => ['ar' => 'جديد', 'en' => 'New'], ...])` is called
- **Then**: The associated `Service` row has updated JSON translations for `name` and `description`; `type`, `center_id`, `slug`, `status` are unchanged
- **Pass Condition**: `$riding->service->refresh()->getTranslations('name')` matches input
- **Evidence**: Post-update DB select + comparison

### AC-6: Update method syncs PriceOptions (delete-then-recreate)
- **Type**: `rule`
- **Given**: Existing `RecreationalRiding` whose service has 2 PriceOptions
- **When**: `update()` is called with a different `price_options` array (e.g., 3 items)
- **Then**: Old PriceOptions are gone; exactly 3 new rows exist with the new values; no stale IDs remain
- **Pass Condition**: Old IDs no longer present, count matches new input, column values match new mapping
- **Evidence**: ID-based deletion check + count + column assertions

### AC-7: Update method syncs Schedules (delete-then-recreate)
- **Type**: `rule`
- **Given**: Existing `RecreationalRiding` with 4 Schedule rows
- **When**: `update()` is called with different `days` and `hours`
- **Then**: Old Schedule rows are gone; new rows exactly cover the new days × hours-slot-pairs; polymorphic FKs still point to the same RecreationalRiding
- **Pass Condition**: Old schedule IDs absent; count and values match new input
- **Evidence**: ID-based deletion check + count + iteration over new expected combinations

### AC-8: Both methods are fully transactional
- **Type**: `rule`
- **Given**: A `create()` or `update()` call where an exception is thrown mid-way (e.g., after Service creation but before PriceOption creation, via a mock or intentionally-bad data triggering a DB error)
- **When**: The exception propagates out of the method
- **Then**: No partial records exist — Service, RecreationalRiding, PriceOption, Schedule tables show zero rows created by this call (rollback applied)
- **Pass Condition**: Count queries on all four tables return the same counts as before the failed call
- **Evidence**: Before/after counts on a transaction that is forced to fail mid-flow

### AC-9: Update uses row-level locking on Service
- **Type**: `rubric`
- **Dimension**: Concurrency safety implementation correctness
- **Scale**: 1-5
- **Anchors**: 1 = no locking or transaction; 3 = transaction present but no lockForUpdate; 5 = DB::transaction + lockForUpdate on the Service row during update before modifying cascading relations
- **Pass Threshold**: >= 5
- **Evidence**: Static code inspection of the `update()` method body — presence of `lockForUpdate()` call chained onto Service query inside transaction closure

### AC-10: Returned RecreationalRiding is eager-loaded and fresh
- **Type**: `rule`
- **Given**: Successful `create()` or `update()` call
- **When**: Accessing `$riding->service`, `$riding->service->priceOptions`, `$riding->schedules`
- **Then**: All three relations are already loaded (no additional lazy-loading queries) and reflect the just-persisted state
- **Pass Condition**: `$riding->relationLoaded('service') === true`, `$riding->service->relationLoaded('priceOptions') === true`, `$riding->relationLoaded('schedules') === true`
- **Evidence**: `relationLoaded()` assertions immediately after method return
